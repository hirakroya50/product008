# GitHub issue → reviewed draft PR

## Selecting the pipeline mode

The issue workflow defaults to `openai`. Set `OPENAI_API_KEY` in repository Actions secrets and `OPENAI_MODEL` as a secret or variable to a Responses API model that supports strict structured outputs. Secrets take precedence over variables. AI mode handles application issues beyond shipping: triage inspects the repository, the Fitter selects justified implementation and regression paths, an independent test engineer prepares acceptance tests, the Developer implements the plan, and a fresh reviewer checks completeness and regressions. The shell runner explicitly approves API usage before triage; execution is limited to 16 API calls with usage recorded in `api-usage.json`. No paid probe runs during standard doctor.

To run the deterministic shipping demo, explicitly set the secret or variable `HARNESS_MODE` to `offline`. Only offline mode is limited to shipping banner/threshold requests. It requires no OpenAI key and its PR summary labels the limited deterministic review.

For local execution, load `.env` with `set -a; source .env; set +a` before running the script. Local `run-issue.sh` defaults to AI mode; `pnpm demo` explicitly uses offline mode. The runner validates API configuration without making a paid probe. Both modes keep network-denied macOS execution, fresh-check requirements, bounded repair and human review. Plan edits are limited to application source, tests, styles and Markdown docs; generated code cannot change dependencies, CI, infrastructure or the harness.

Push this workflow and the harness changes to the repository's default branch before creating the test issue. The default branch may be `main` or the currently selected branch; the workflow discovers it automatically. GitHub issue events only run workflows present on the default branch.

1. Rotate the hosted Valkey password if it was shared in chat. In GitHub repository Settings → Secrets and variables → Actions, add a repository secret named `VALKEY_URL` with the complete newly issued `rediss://...` connection URL. Preserve the provider's hostname, credentials and port exactly. Do not commit `.env` or put this URL in an issue.
2. In repository Settings → Actions → General → Workflow permissions, enable **Allow GitHub Actions to create and approve pull requests**. The workflow itself requests only contents write, issues read, and pull requests write. It creates draft PRs and never approves or merges them.
3. Commit and push the new workflow and harness files using your IDE. Confirm the workflow is on the default branch and Actions is enabled.
4. As the repository owner, create an issue titled **Change the free shipping threshold to $100**. Body: **Update the free shipping progress banner in CartDrawer to use a $100 threshold. Keep subtotal and stock behavior intact, clamp progress at 100%, and show unlocked messaging at or above $100.** No label is required.
5. Open Actions → **Product 008 - Reviewed issue to draft PR** → the run for the issue. It executes intake → repository triage → fitted plan and immutable acceptance tests → developer → seven quality checks and independent review → bounded repair if needed → local commit → 15-case audit → publication integrity check → branch push → draft PR.
6. Open the draft PR and review the code diff and the run summary. Download the run's artifact to inspect `intake.json`, `diagnosis.json`, `draft.json`, patch/test records, logs, evidence and PR summary. The human gate is your decision to review and merge; no automatic merge is configured.
7. Reopen the issue or use **Run workflow** with an issue number to retry after correcting configuration. If the default branch already contains the requested threshold, the run verifies it and reports that no new PR is required. For a second demo after merging $100, request $125.

In offline mode, banner additions and shipping threshold changes from $10 to $1000 are supported. AI mode selects scope from the complete issue and repository; ambiguous or unsupported requirements stop at triage with a diagnosis artifact. There is no target file count: a two-file threshold change can be complete, while a broader feature must include every required integration. Only OWNER/MEMBER/COLLABORATOR-authored issues trigger automatically; manual dispatch requires normal repository access. The workflow uses a GitHub-hosted macOS 15 runner because the existing tester uses the native macOS sandbox. Runner availability and permissions are validated by the first actual hosted run.

For local testing, set `VALKEY_URL` in a local `.env`, load it with `set -a; source .env; set +a`, authenticate `gh auth login`, and run `bash scripts/run-issue.sh NUMBER` from a clean checkout. The local script produces a commit and summary; only the workflow's publication step pushes and creates a remote PR.

Hosted Valkey uses TLS when the URL scheme is `rediss://`; certificate verification stays enabled. With no explicit port, the Redis client uses 6379. If the provider requires another port, use the exact full URL from its dashboard. A connection, auth or TLS failure fails readiness. Credentials are never embedded in workflow source.

See [GitHub issue workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#issues) and [Actions PR permissions](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository).

The shared Valkey client explicitly sets TLS SNI to the URL hostname for hosted routing, keeps certificate verification enabled, allows 15 seconds for database wake-up, and bounds startup to three attempts. Both doctor and worker leases use this adapter. Connection errors report a sanitized underlying error code instead of only `Connection is closed.` See [Layerbase TLS routing requirements](https://layerbase.com/docs/cloud/connecting/redis).

## Company rollout and evidence

The commit gate requires typecheck, production build, all regression tests, formatting of changed files, diff hygiene, executed independent acceptance tests for every AC ID, and review without P0–P2 findings. Acceptance tests are stored before development and injected into the sandbox; Developer/Fixer cannot edit their contract. Every test and review cycle is saved, and a repair that produces no code change stops for investigation. The PR summary contains actual changed files with rationale, criteria evidence, verification results, review findings, risks, manual checks and the commit SHA. Logs and API usage are in the workflow artifact.

The `PR quality` workflow validates PR updates without API keys or repository write permissions. Configure branch protection to require its `quality` job and a maintainer review. Generated PRs remain drafts; this harness never auto-merges. PR events created with `GITHUB_TOKEN` can put CI runs into an approval-required state. In the PR merge box, select **Approve workflows to run** if GitHub shows that banner, then wait for the quality check before merging. See [GitHub token workflow behavior](https://docs.github.com/en/actions/concepts/security/github_token).

This change does not turn the existing sandbox into production isolation. It still shares host read access and dependencies. Validate company requirements for runner isolation, repository data sent to the configured API, retention, browser/integration checks and branch protection before rollout. The system reports tests that ran and leaves visual/manual validation explicit; AI review is additional evidence, not a guarantee.

## Triage assumptions and blocking questions

A clear request to change the free-shipping threshold to $250 should proceed without asking whether the existing Navbar and App copy for that same offer also needs updating. Triage records the assumption to keep that offer consistent and passes it to the Fitter, Developer, acceptance-test engineer and reviewer. An explicit instruction to change only the banner or leave specific copy unchanged overrides that default.

When the initial triage still raises questions, a single additional resolution request classifies each one as blocking or safely inferable, with an assumption and source/issue rationale for every resolved question. The harness rejects missing, duplicated or unjustified resolutions. Unsupported changes and genuinely unspecified business rules remain blocked. The original diagnosis is preserved in `triage-initial.json`, any second assessment in `triage-resolution.json`, and the final decision in `diagnosis.json`. The same 16-request limit includes this extra assessment. Implementation assumptions are retained in `draft.json` and the PR summary for review.
